The bounded fake-only adapter is appropriate. Requests must be strict canonical UTF-8 JSON objects with exact format/version/provider/operation/input fields and bounded total bytes; reject duplicate/unknown/missing fields, booleans where integer expected, nonfinite values, malformed input, unknown provider/operation and oversized content before output creation. The fake implementation must be deterministic and prove no shell/network/credential lookup. A receipt must bind exact request and response bytes, provider/adapter/status/timestamps and response digest; verifier must re-read bounded bytes, enforce canonical schema and detect request/receipt/response tamper and drift.

Strongest challenge: failure paths can accidentally create a receipt, ledger event or credential-bearing copy before provider validation. Validate provider and complete request before exclusive external output; external output must be outside project, reject aliases/symlinks/traversal/internal paths and existing targets, clean only owned staging on failure, and leave ledger/events unchanged. Repeated fake dispatch should yield deterministic response semantics while timestamps are explicitly observational and not a reproducibility proof. Ordinary receipt evidence registration must use existing gates and detect receipt drift.

Plan acceptance requires CLI exit codes, malformed/size/duplicate/noncanonical/bool/nonfinite/unknown-provider/unknown-operation checks, no-ledger-mutation failure assertions, tamper/overwrite/path/symlink verification, deterministic repeated fake result, ordinary evidence registration, and actual source inspection proving no subprocess/network/credential calls. Preserve explicit limits: fake does not establish provider compatibility, identity, authorization, hosted reliability, retry/idempotency, remote custody or production deployment.
