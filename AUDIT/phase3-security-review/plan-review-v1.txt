Independent findings and planned acceptance conditions:
1. Sign a deterministic, bounded, versioned canonical payload covering principal,
   namespace/protocol, first-event identity, event head and complete state digest.
   Require operator-supplied external SHA256 pin and separately authorized key
   policy; signature validity alone must not be reported as trusted authorization.
2. A signed audit summary is the signer's assertion of observed file checks at
   capture time. Historical event bytes cannot prove past live-file availability.
   Verify bound ledger prefix/state exactly, separately compute current audit,
   explicitly disclose historical-prefix signatures and require-current failures.
3. Avoid nested locks: existing Project.audit acquires project_lock. Reopen ledger
   under lock afterward and reject a differing audit count/head. Hold capture lock
   through sign/publish; the lock still cannot stop arbitrary editor/OS writers.
4. Keys, allowed-signers/revocations and trusted pins are external operator inputs.
   Snapshot public policy and payload bytes for subprocess verification to avoid
   check/use ambiguity, never archive private key contents. Key rotation requires
   new policy/key, new signed bundle and new externally distributed pin. Revocation
   must actually use OpenSSH -r, not merely record a revoked metadata label.
5. Strict payload parsing should reject duplicate JSON keys, nonfinite values,
   unsupported fields/types/versions, excessive size, broken signatures, bad pins,
   unauthorized principals/keys, wrong namespace, aliases/symlinks and unsafe
   output destinations. Subprocesses must use argv/no shell and bounded timeout.
6. Rehash-forged local histories, truncated rollback and changed state must fail
   against unchanged authorized signatures and pins. Signing and verification
   must preserve ledger events/projections and never overwrite an output bundle.

Actual independent evidence: openssh-plan-probe-v1.json contains 11 executed

Alternative: an authenticated remote timestamp/append-only identity service gives
stronger global freshness and key lifecycle, preferable for mutually untrusted
distributed deployment; it introduces credentials/service/deployment ownership.
Pure-Python cryptography creates unnecessary maintenance/correctness risk. An
optional external OpenSSH boundary is appropriate for this bounded additive task
provided current/history and external-policy limitations remain explicit.
