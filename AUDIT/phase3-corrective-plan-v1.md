Date: 2026-10-14. Status: proposed; not an approved implementation plan.

T000010 event 818 records completion, but the actual independent reviewers
reject D17/D18 as genuine execution of their required three-round process.
The temporary runner omitted integrity preconditions and supplied proxy
reviewer records. Renewed security inspection also found concrete source

Preserve all original records. Treat this as an additive major corrective
task with explicit supersession/disposition, not an edit to past completion.

## Recommended order

1. Finish the full read-only integrity audit: SQLite consistency, every event
   sequence/hash/link, final state equality, complete JSON journal, all
   generated Markdown and session reports, all current evidence and every
   promised historical snapshot. Preserve the four known legacy losses.
2. Record the governance correction through the maintained CLI under the
   actual root identity. If normal CLI execution remains resource-limited,
   record the limitation in maintained project memory and audit reports.
3. Create a major corrective task covering coordination source/tests/docs and
   new uniquely versioned evidence. Actual assigned reviewers must personally
   read/acknowledge the exact reports and perform their own debate rounds.
4. Enforce per-instance TTL limits in acquire and renew; make backend/token
   identities instance-specific without claiming authentication; reject clocks
   whose requested expiry cannot be represented; percent-encode SQLite file
   URIs and refuse missing metadata without creating files.
5. Validate cross-instance rejection, configured TTL maxima, large finite time
   behavior, special-character and missing-project paths, and unchanged bytes
   during every benchmark. Then run the full regression and scaffold checks.
6. Obtain genuine current result consensus and audit before accepting the
   corrective task. Preserve prior request_changes and explicitly distinguish
   accepted implementation from rejected historical review attribution.
7. Scope a separate major history-performance task. Prefer bounded-memory
   streaming and byte-identical projection verification without changing the
   schema or authority. Require equivalence, corruption, interrupted-write and
   realistic-history tests. Never cache away integrity checks without an
   explicit reviewed trust model.

## Alternatives and recovery

Keeping the present implementation would retain known boundary defects.
Rebuilding the ledger architecture would exceed the user's intended additive
scope and discard validated behavior. The preferred approach is a reviewed
local correction, with scalable-history work isolated as a separate integrity
change. If resources prevent required gates, retain the complete evidence and
an explicit unresolved status; do not manufacture reviewer participation.

## Remaining Phase 3 scope

Real provider invocation, authenticated remote leases, hosted platform matrix
runs, systematic research retrieval and real-domain scientific validation are
still unvalidated. The completed earlier trust, manifest and dispatch boundary
increments do not establish those broader production claims.
